## Часть 3. Права на файлы и каталоги

### Права созданных каталогов

Вывод команды `sudo ls -ld /DATA /DATA/sec1 /DATA/sec2 /DATA/sec3`:

    drwxrwx---  5 root project 4096 Nov 25 12:08 /DATA
    drwxrwxrwt  2 root root    4096 Nov 25 12:08 /DATA/sec1
    drwxr-----  2 u1   readers 4096 Nov 25 12:08 /DATA/sec2
    drwxr-xr-x  2 root root    4096 Nov 25 12:08 /DATA/sec3

Вывод команды `sudo ls -l /DATA/sec3/nano`:

    -rwsr-xr-x 1 root root 303960 Nov 25 12:08 /DATA/sec3/nano

### Объяснение прав

- **/DATA** (770): владелец root, группа project. Владелец и группа могут читать, писать, выполнять. Остальные — ничего.
- **/DATA/sec1** (1777): sticky bit (виден как `t` в конце). Все могут читать, писать, выполнять. Удалять файлы может только их владелец, владелец каталога или root.
- **/DATA/sec2** (740): владелец u1, группа readers. u1 может всё, группа readers — только читать, остальные — ничего.
- **/DATA/sec3/nano** (4755): SUID бит (виден как `s` в позиции владельца). Владелец root, все могут читать и выполнять. При запуске программа выполняется с правами root.

### Риск SUID от root

Если исполняемый файл принадлежит root и имеет SUID бит, любой пользователь может запустить его с правами root. Если в программе есть уязвимость (например, возможность вызова shell), злоумышленник получит полный доступ к системе.

### Проверка ограничений sudo

- Смена пароля u2 через sudo: успешно (попросила пароль u1 и сменила пароль u2)
- Смена пароля root через sudo: отказано ("извините, пользователь u1 не имеет права запускать /usr/bin/passwd root")
- Запуск sudo ls /root: отказано (u1 не имеет права запускать эту команду)

### Обход ограничений sudo

Правила с подстановочными знаками (*) опасны, потому что позволяют передать аргументы, которые заставят программу выполнить произвольный код. Например, sudo vim позволяет выйти в shell через :!bash. В нашем правиле используется [A-Za-z]*, что теоретически позволяет передать аргумент, но команда passwd не имеет таких уязвимостей.

### Результаты эксперимента с SIGHUP и nohup

- Без nohup: после закрытия SSH-сессии процесс script32 завершился, файл ~/script32.log перестал обновляться. Причина: терминал послал процессу сигнал SIGHUP при закрытии.
- С nohup: процесс продолжил работать после закрытия SSH, файл продолжал обновляться. PPID процесса изменился на 1 (или PID systemd), потому что процесс "осиротел" и был усыновлён init-процессом.

### Различия сигналов

- SIGTERM (15): просьба завершиться, процесс может перехватить и сохранить данные
- SIGKILL (9): принудительное завершение, процесс не может перехватить
- SIGHUP: посылается при закрытии терминала, по умолчанию завершает процесс
- SIGSTOP: останавливает процесс, SIGCONT: возобновляет

## Ответы на вопросы

**1. Зачем при создании SSH-ключа предлагается задать парольную фразу?**
Парольная фраза защищает закрытый ключ на случай его кражи. Если злоумышленник получит файл закрытого ключа, он не сможет им воспользоваться без знания парольной фразы. Это дополнительный уровень безопасности поверх файловой системы.

**2. Зачем при первом подключении по SSH клиент показывает отпечаток ключа сервера и просит подтвердить его?**
Это защита от MITM-атак (атак "человек посередине"). Клиент сохраняет отпечаток в ~/.ssh/known_hosts. Если при следующем подключении отпечаток изменится, клиент выдаст предупреждение "REMOTE HOST IDENTIFICATION HAS CHANGED", так как это означает, что мы подключаемся не к тому серверу (или его ключ был скомпрометирован/переустановлен).

**3. Если у двух пользователей одинаковые пароли, можно ли понять это по /etc/shadow?**
Нет, нельзя. Хэши паролей в /etc/shadow содержат случайную "соль" (salt), которая добавляется к паролю перед хэшированием. Соль генерируется случайно для каждого пользователя, поэтому даже одинаковые пароли дают разные хэши. Формат хэша: $тип$соль$хэш.

**4. Таблица атрибутов прав:**

| Атрибут | Сокращение | Для файла | Для каталога |
|---------|------------|-----------|--------------|
| Read | r | Чтение содержимого файла | Просмотр списка имён файлов (ls) |
| Write | w | Изменение содержимого файла | Создание, переименование, удаление файлов внутри каталога |
| Execute | x | Запуск файла как программы | Вход в каталог (cd) и доступ к файлам по имени |
| SUID | s (в позиции владельца) | Запуск программы с правами владельца файла, а не запустившего | Игнорируется в Linux |
| SGID | s (в позиции группы) | Запуск программы с правами группы-владельца | Новые файлы и подкаталоги наследуют группу каталога |
| Sticky Bit | t (в конце строки прав) | Игнорируется | Удалять и переименовывать файлы могут только их владелец, владелец каталога и root |

**5. Почему для удаления файла нужны права на каталог, а не на файл?**
Удаление файла — это изменение содержимого каталога (удаление записи о файле из каталога). Поэтому нужны права w и x на каталог. Sticky bit на каталоге добавляет ограничение: даже при наличии прав w и x на каталог, пользователь может удалить только те файлы, владельцем которых он является (или если он владелец каталога/root). Это защищает файлы в общих каталогах типа /tmp.

**6. Команда setfacl для выдачи прав конкретному пользователю:**

    setfacl -m u:имя_пользователя:rwx файл

Для задания 3 из Части 3 (выдать u4 и u5 права только на чтение /DATA/sec2) можно использовать ACL без создания дополнительной группы:

    setfacl -m u:u4:r-x /DATA/sec2
    setfacl -m u:u5:r-x /DATA/sec2

Это позволяет дать права конкретным пользователям без изменения владельца или группы каталога.

**7. Чем различаются su, su - и sudo?**
- su — переключает пользователя, но сохраняет окружение текущего пользователя (переменные среды, рабочий каталог)
- su - — выполняет полноценный вход с окружением целевого пользователя (как при логине), загружает профиль
- sudo — выполняет одну команду с правами другого пользователя (по умолчанию root), запрашивая пароль текущего пользователя

В Debian рекомендуют sudo, потому что: не нужно раздавать пароль root, каждое действие логируется в /var/log/auth.log, работает принцип наименьших привилегий, можно давать ограниченные права конкретным пользователям.

**8. Удалось ли обойти ограничение sudo?**
Нет, не удалось (если правило написано корректно). Правила с подстановочными знаками (*) опасны, потому что позволяют передать аргументы, которые заставят программу выполнить произвольный код. Например:
- sudo vim → внутри vim можно выполнить :!bash и получить shell с правами root
- sudo less /etc/passwd → внутри less можно нажать !bash
- sudo find / -exec bash \; → выполнит bash с правами root

Поэтому в sudoers нужно указывать конкретные команды без wildcard или использовать строгие паттерны.

**9. Чем отличается SIGTERM от SIGKILL?**
- SIGTERM (сигнал 15) — просьба завершиться. Процесс может перехватить этот сигнал, сохранить данные, закрыть файлы и корректно завершиться. Это "вежливое" завершение.
- SIGKILL (сигнал 9) — принудительное завершение. Процесс не может перехватить этот сигнал, он уничтожается ядром немедленно. Данные могут быть потеряны, файлы не закрыты корректно.

Процесс может перехватить SIGTERM, но не может перехватить SIGKILL.

**10. Что происходит с процессом, запущенным через &, при закрытии SSH-сессии?**
При закрытии SSH-сессии терминал посылает всем своим дочерним процессам сигнал SIGHUP (hangup), который по умолчанию завершает их. Процесс получает сигнал и завершается.

nohup меняет это поведение, заставляя процесс игнорировать сигнал SIGHUP. Процесс продолжает работать после закрытия терминала.

PPID процесса с nohup становится равен 1 (или PID systemd), потому что после закрытия родительского процесса (терминала/ssh) процесс "осиротел" и был усыновлён init-процессом (systemd с PID 1).

**11. Что такое зомби-процесс?**
Зомби-процесс — это процесс, который уже завершился (выполнил exit), но его родитель не считал код возврата (не вызвал wait() или waitpid()). Процесс находится в состоянии Z (zombie).

Зомби не занимает память и ресурсы CPU, только строку в таблице процессов. Убить его kill -9 нельзя, потому что он уже мёртв — сигнал некому обрабатывать. Чтобы убрать зомби, нужно завершить его родительский процесс (тогда зомби будет усыновлён init, который считает код возврата).

**12. Чем отличается вывод sshd -T от строк, найденных в sshd_config через grep?**
grep показывает только те строки, которые явно прописаны в файле sshd_config. sshd -T показывает эффективные настройки, которые реально использует сервер, включая:
- Значения по умолчанию (если параметр не указан в файле)
- Параметры из файлов каталога /etc/ssh/sshd_config.d/ (они имеют приоритет)
- Результат обработки директив Match и Include

Например, если в sshd_config не указан параметр Port, grep ничего не найдёт, а sshd -T покажет port 22 (значение по умолчанию).

**13. Какой риск возникает, если владельцем исполняемого файла будет root и на этот файл будет установлен suid?**
Любой пользователь системы сможет запустить эту программу, и она будет выполняться с правами root (UID 0), а не с правами запустившего. Если в программе есть уязвимость (например, возможность вызова shell, переполнение буфера, инъекция команд), злоумышленник сможет получить полные права root в системе.

Пример: если скопировать /bin/bash с SUID от root, любой пользователь сможет запустить его и получить root-shell. Поэтому SUID-файлы от root — потенциально опасные объекты, и их нужно минимизировать.

## Понятийный минимум (самопроверка)

1. **Учётная запись, UID, GID, основная и дополнительные группы; файлы /etc/passwd, /etc/group, /etc/shadow**
Каждый пользователь имеет UID (числовой идентификатор) и GID (основная группа). Дополнительные группы дают доступ к общим ресурсам. /etc/passwd хранит основные данные пользователей, /etc/group — группы, /etc/shadow — хэши паролей (доступен только root).

2. **Права доступа rwx для владельца, группы и остальных; восьмеричная запись; umask**
Права: r=4, w=2, x=1. Например, rwxr-x--- = 750. Umask вычитает биты из 666 (файлы) или 777 (каталоги) при создании новых файлов.

3. **Особенности прав для каталогов; suid, sgid, sticky bit**
Для каталога: r — просмотр списка, x — вход и доступ к файлам, w — создание/удаление файлов. SUID — запуск с правами владельца, SGID — запуск с правами группы (на каталоге — наследование группы), sticky bit — удаление только владельцем файла.

4. **SSH: клиент и сервер, отпечаток ключа сервера, known_hosts**
SSH создаёт шифрованный канал. Сервер sshd слушает порт 22. При первом подключении клиент сохраняет отпечаток ключа сервера в ~/.ssh/known_hosts для защиты от MITM-атак.

5. **Пара ключей (открытый и закрытый), authorized_keys, парольная фраза**
Ключ — пара файлов: закрытый (остаётся у клиента) и открытый (копируется на сервер в ~/.ssh/authorized_keys). Закрытый ключ можно защитить парольной фразой.

6. **su, sudo, sudoers, sudoers.d, visudo, принцип наименьших привилегий**
su переключает пользователя, sudo выполняет команду с правами другого пользователя. Правила хранятся в /etc/sudoers и /etc/sudoers.d/. Редактировать только через visudo. Принцип наименьших привилегий: давать минимально необходимые права.

7. **Процесс, PID, PPID, дерево процессов, состояния процесса, зомби-процесс**
Процесс — экземпляр программы. PID — идентификатор, PPID — идентификатор родителя. Дерево процессов начинается с systemd (PID 1). Состояния: R (выполняется), S (спит), Z (зомби). Зомби — завершившийся процесс, родитель не считал код возврата.

8. **Сигналы SIGTERM, SIGKILL, SIGHUP, SIGSTOP, SIGCONT**
SIGTERM (15) — просьба завершиться, SIGKILL (9) — принудительное завершение, SIGHUP — при закрытии терминала, SIGSTOP — остановить, SIGCONT — продолжить.

9. **Фоновые задания: &, jobs, fg, bg, nohup, disown**
& — запуск в фоне, jobs — список заданий, fg — на передний план, bg — продолжить в фоне, nohup — игнорировать SIGHUP, disown — отсоединить от оболочки.

10. **Функции bash**
Функции позволяют оформить повторяющиеся фрагменты кода. Синтаксис: имя() { команды; }. Вызов: имя аргументы.
